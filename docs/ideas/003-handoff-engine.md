# Заметка для рабочего чата: движок графа под удалённые команды

Контекст: [003-remote-control.md](003-remote-control.md). Сама фича (MQTT/HTTP, ноды команд) — в фазе 2, но эти решения дешевле принять **при проектировании движка в фазе 1**.

## Что заложить

1. **`Event` несёт данные.** Сейчас в спеке (3.3) `Event` — голый импульс с timestamp. Нужно: `Event` = `{ts, payload?: Json, ctx?: RequestContext}`. Обычные события (фронт, таймер) — без payload; события команд/сети — с данными. Ноды, которым всё равно, просто игнорируют payload.

2. **Контекст запроса (`Request`) проходит по графу.**
   - Новый тип сокета `Request` (непрозрачный: id запроса, транспорт, дедлайн). Нода `Ответ` принимает его явным проводом.
   - Плюс неявное распространение: контекст едет с волной-транзакцией (3.4) от ноды `Команда`, чтобы ноды-посредники (Map Range, Арбитр, Clamp) не обязаны были его прокидывать, а `Ответ` мог взять его из волны, если провод `Request` не подключён.
   - Движок фиксирует завершение волны → можно автоматически подтвердить команду без `Ответ`, и отследить таймаут ответа.

3. **Источники событий извне.** Engine должен принимать «внешние» входы (команды из транспорта, значения UI-контролов) как начало новой транзакции с контекстом — единым механизмом с GPIO-фронтами и таймерами.

4. **Реестр объявлений проекта.** При загрузке графа собирать из нод `Команда` / `Состояние` / событий манифест API проекта (имена + схемы) — он нужен для discovery, HA, проверки конфликтов имён между запущенными проектами (как захват выходов, 3.5).

5. **Нода `Арбитр` (last-writer-wins)** — тривиальна, но требует, чтобы у значения можно было узнать источник/время → в волне хранить «кто инициировал» (GPIO/таймер/UI/remote:<transport>).
