# 002 — Что учесть в napi-pIOneer по документации производителя

- **Статус:** принято, для передачи в рабочий чат
- **Источник:** выжимка `napiworld.ru/software` + techblog → `.claude/skills/napi-c/vendor-docs.md`
- **Задевает спеку:** 2 (ограничения), 3.1 (описание платы), 3.5 (захват ресурсов), 3.7 (ноды UART), 6 (безопасность/восстановление); идея [001](001-modules-and-simulation.md)

## Сделать / учесть

1. **Системные пины — из живого Device Tree, а не только из `uEnv.txt`.**
   Читать `/sys/firmware/devicetree/base` (или `/proc/device-tree`): узлы `uart*`, `i2c*`, `spi*`, `pwm*` со `status = "okay"` + их `pinctrl-0` → какие пины заняты. Это учитывает `user_overlays`, ядерные драйверы (`gpio-leds`, `rts-gpios`) и любые ручные правки. `uEnv.txt` — только для подсказки «что включится после reboot». `pinmux-pins` на vendor-ядре бесполезен.

2. **Понятные ошибки занятости.** `EBUSY` при запросе линии = пин держит драйвер ядра → HAL отдаёт «J10-17 занят драйвером ядра (RS-485 DE для uart1)». Для UART перед открытием проверять, не держит ли порт другой процесс (`serial-getty@ttyS2`, `mbusd`, telegraf) — `/proc/*/fd` → имя процесса/юнита, и предлагать его остановить.

3. **RS-485 в ноде UART.** Режим «RS-485» с DE-пином делать **ядром** (оверлей с `rts-gpios` / аппаратный RTS UART1), а не переключением GPIO из Python — тайминги на 115200+ из userspace не попасть. До фазы с управлением оверлеями: нода UART показывает, включён ли rs485-режим в DT (`linux,rs485-enabled-at-boot-time`), и даёт рецепт оверлея. Modbus RTU — через `pymodbus`/`minimalmodbus` (есть на плате) поверх этого порта; эмулятор `modbus-slave` от lab240 — для тестов.

4. **Модули с ядерными драйверами (дополнение к 001).** Часть железа правильно подключать не userspace-драйвером, а **ядерным через DT-оверлей**, а модуль лишь пользуется результатом:
   - RTC DS3231/DS1338 → `/dev/rtcN`;
   - LED с триггерами → `gpio-leds`;
   - кнопки с ядерным debounce → `gpio-keys` (`/dev/input/eventN`);
   - **энкодер** → `rotary-encoder` (input events, без потерь фронтов) — альтернатива gpiod-квадратуре;
   - **DS18B20 (1-Wire)** → `w1-gpio` — из userspace его не сделать вообще (тайминги в микросекундах);
   - RS-485 DE, W5500, spidev.
   Значит, в `module.yaml` нужно поле `requires_overlay` (готовый `.dtbo` в модуле или шаблон с подстановкой пинов), а установка такого модуля = «добавить оверлей + reboot» → зависит от фазы управления оверлеями (спека, фаза 3). В mock/стенде такие модули моделируются на уровне результата (`/dev/input`, rtc), а не протокола.

5. **Конфликт I2C3 m0 ↔ PWM2/3 подтверждён**: оверлей `rk3308-i2c3-m0` явно выключает `pwm2`/`pwm3`. В `boards/napi-c.yaml` и в подсказках UI: аппаратный PWM на J9-11/13 = отключить i2c3-m0.

6. **Board-профили / комплекты.** Помимо голой Napi-C — пресет **NapiSci** (OLED SSD1306 по SPI2 + DC/RST на gpiochip2, реле J10-4, LED J9-13, кнопка J9-11, BH1750/BME280/SHT30 на I2C1, RTC). Это готовый набор первых модулей и тестовый сценарий; вендорные скрипты (`lab240/napi-scripts`) — референс драйверов (переписывать на HAL, без `gpioset` через subprocess). Также учесть модификации (FCC3308, FCU3308P…) — разные mux-варианты, поэтому `boards/*.yaml` на модификацию.

7. **Безопасность/восстановление — в UI и доках проекта.** Перед любой будущей правкой `uEnv.txt` показывать путь восстановления: microSD с системой (приоритет загрузки), консоль UART0 **1 500 000** (вендорские доки про 115200 устарели для 0.3.x), maskrom + rkdeveloptool.

8. **Идентичность устройства.** Стабильный ID платы для проекта/лицензий/обнаружения — 5 байт OTP с offset 20 (как в `napi-board-config`), не рецепт из блога.

9. **Персистентность.** (Найдено рабочим чатом) soft_reset стирает весь p7, кроме dot-каталогов → данные и код pioneer — в `/mount/rfs/rw/.pioneer/`. Отразить в спеке (раздел 2/9), где сейчас указан `/mount/rfs/rw/pioneer/`.
