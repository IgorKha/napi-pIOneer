# 006 — Симуляция для отдельного проекта, скрипта и блока (не только глобальный режим)

- **Статус:** принято (замечание пользователя 2026-10-11: «не увидел в блоках режим симуляции — чтобы тестировать до подключения железа»)
- **Задевает спеку:** 3.5 (захват ресурсов), 4 (UI: редактор проектов/блоков/скриптов), 5 (HAL/HW); идеи [001](001-modules-and-simulation.md) (стенд, модели модулей)
- **Когда вливать:** архитектурная часть (HW на «пространство») — до дальнейшего роста HAL; UI — следующей фичей.

## Что сейчас

Симуляция есть только как **глобальный режим всего сервиса**: `hal = "bench"` в `config.toml` + перезапуск. На плате стоит `hal = "linux"` → стенда нет вовсе (`/bench` отдаёт 404), а в редакторе проектов, Python-блоков и скриптов нет переключателя. Стенд виден только на странице «Плата» и только в bench-режиме.

## Идея

Любой запуск можно сделать **в симуляции**, не трогая остальных: на одной плате одновременно работают «боевые» проекты на железе и проекты/скрипты/блоки на виртуальной плате.

## Решения (предлагаемые)

1. **Два пространства железа: `real` и `sim`.** Каждое — свой `HW` = (`HAL`, `ResourceManager`): `real` — LinuxHAL (на Mac — BenchHAL, как сейчас), `sim` — всегда отдельный `BenchHAL` той же платы. Захваты в `sim` не конфликтуют с `real` и железо не трогают никогда. Все sim-запуски делят **одну виртуальную плату** (как на настоящей — конфликты между sim-проектами ловятся).
2. **Режим — свойство запуска, сохраняется в метаданных** проекта/скрипта: «Железо / Симуляция». `ProjectHW`, `_Runner` скрипта и blockhost берут HW своего пространства. Глобальный `hal = "bench"` остаётся для разработки на Mac (тогда оба пространства — стенд).
3. **Модели на стенде создаются автоматически** по hardware-нодам/ресурсам sim-запуска: кнопка, LED/реле, потенциометр (ADC-слайдер), soft-PWM (шкала скважности), UART (терминал/петля), I2C-устройства — модели модулей (001); ручные модели (перемычка, источник напряжения) — как сейчас.
4. **Управление — прямо на нодах.** В sim-режиме hardware-ноды в графе получают мини-виджеты: «нажать» у кнопки, свечение у LED/реле, слайдер у ADC, экран у дисплея. Board-нода и страница «Плата» показывают **виртуальную плату** этого пространства (переключатель «железо / симуляция»).
5. **Тест-стенд Python-блока.** В редакторе блока — вкладка «Проверить»: блок запускается один, в sim-пространстве, для каждого `In` — контрол (тумблер/слайдер/поле/кнопка события), `Out` — живые значения и лог; железо блока (`self.hw`) — в `sim`. Без создания проекта.
6. **Скрипты** — тот же переключатель «Запустить в симуляции» (worker получает RPC к sim-HW).
7. **Сеть в симуляции** — по умолчанию настоящая (симулируется железо, не мир), но sim-проект помечен в `describe`/HA и в логах команд; опция «изолировать сеть» (HTTP/MQTT-ноды не отправляют наружу, а пишут в лог) — позже.
8. **Видимость.** Всё в sim помечено (фиолетовый бейдж SIM у проекта, рамка канваса, префикс в логе), чтобы не перепутать с работающим на железе. Переключение sim → железо: предупреждение со списком пинов и подсказками подключения из модулей/справки.
9. **Сценарии** (записанные воздействия, автотесты проектов на стенде) — по-прежнему в последнюю очередь (001 п.10), но поверх этого же sim-пространства.

## Критерий готовности

На плате (`hal = linux`) один проект управляет настоящим реле, параллельно второй проект «Термостат» запущен **в симуляции**: в его графе на ноде ADC двигаю слайдер → гистерезис → нода реле светится; настоящие пины не меняются, захваты `sim` не мешают `real`. Python-блок «Гистерезис» проверяется во вкладке «Проверить» без проекта.

## Решено (2026-10-11)

1. **Одна общая виртуальная плата** на все sim-запуски — конфликты пинов между sim-проектами видны, как на настоящей.
2. **Состояние виртуальной платы сохраняется** между перезапусками сервиса (модели, их настройки и значения: положения слайдеров, уровни, содержимое ручных моделей) — `data/sim-bench.json`, атомарная запись, с дебаунсом; кнопка «Сбросить виртуальную плату».
3. **Гибрид нужен:** в одном проекте часть ресурсов на железе, часть в симуляции (настоящий датчик + виртуальное реле).

## Гибрид — как устроено

- Пространство (`real`/`sim`) выбирается **на уровне ресурса**, а не только запуска: у проекта/скрипта есть режим по умолчанию («Железо» / «Симуляция» / «Гибрид»), в гибриде у каждой hardware-ноды (и у каждого ресурса скрипта) — переключатель `real`/`sim`, сохраняется в графе (параметр ноды `space`, по умолчанию — режим проекта).
- `ProjectHW` / `_Runner` маршрутизируют каждый захват в HW нужного пространства по `(ресурс → space)`; захват `J9-7` в `sim` и `J9-7` в `real` — разные ресурсы (разные `ResourceManager`), поэтому гибридный проект может, например, читать настоящий `J10-2` и «нажимать» виртуальный `J10-2` другого sim-проекта без конфликта.
- Шины: пространство задаётся на устройство (`i2c1@0x76` настоящий датчик, `i2c1@0x3c` виртуальный дисплей) — шина в каждом пространстве своя.
- SDK скриптов: `Output("J9-7", sim=True)` / `I2C("i2c1", 0x3C, sim=True)` переопределяют режим скрипта для ресурса; режим скрипта задаёт умолчание.
- UI: на ноде — бейдж `SIM`/`HW` и переключатель в инспекторе; Board-нода в гибриде показывает обе платы (вкладки) с подсветкой, какой пин в каком пространстве; валидация предупреждает, если провод соединяет sim-выход с логикой, которая управляет real-выходом (это нормально, но стоит видеть).
- Безопасность: переключение ресурса `sim → real` у запущенного проекта — только через «Применить» (перезапуск) с подтверждением и списком реальных пинов, которые начнут управляться.
