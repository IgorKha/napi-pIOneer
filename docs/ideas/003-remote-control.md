# 003 — Удалённое управление: команды, ответы и телеметрия (MQTT / HTTP)

- **Статус:** принято (концепция), детали — черновик
- **Задевает спеку:** 3.3 (типы сокетов: `Event` с данными, новый `Request`), 3.4 (семантика исполнения), 3.7 (каталог нод: Сеть), 5.1 (API), 6 (безопасность), 10 (фазы: MQTT переезжает из фазы 3 раньше)
- **Когда вливать:** изменения движка (события с данными + контекст запроса) — **в фазе 1, сейчас** (см. [003-handoff-engine.md](003-handoff-engine.md)); транспорт и ноды — в фазе 2 вместе с сетевыми нодами.

## Идея

Внешний сервер (в той же локальной сети) шлёт плате **команды**, проект (граф или скрипт) превращает их в действия на подключённых устройствах и **отвечает**. Плата также сама публикует **телеметрию и события**. Пример: крутилка управляет сервой локально, а сервер может перехватить управление командой `servo.set`.

## Решения

1. **У проекта есть своё API — объявленные команды.** Команда = имя (`servo.set`) + схема аргументов (`angle: Number, min 0, max 180`) + опц. схема ответа. Удалённо вызвать можно **только объявленные команды** (никакого «выставь любой пин» по сети, если пользователь сам такую команду не сделал).
2. **Ноды:**
   - `Команда` (вход) — параметры: имя, схема аргументов. Выходы: `Event` (пришла, с данными), поля аргументов по схеме (`Number`/`Bool`/`String`/`Json`), `Request` (контекст запроса).
   - `Ответ` — входы: `Request`, значение (`Json`/любой), `ok: Bool`, опц. текст ошибки. Отвечает именно на тот запрос. Если граф не ответил за `timeout` (по умолчанию 5 с) — сервис сам отвечает `{"ok": false, "error": "timeout"}`. Команда без ноды `Ответ` подтверждается автоматически (`ok: true` после обработки волны).
   - `Публикация` — отправить событие/значение в топик/канал (по событию или по изменению).
   - `Состояние` — значение, которое публикуется при изменении (retained) и доступно серверу по запросу.
   - `Связь` — источник: `Bool` online, `Event` потеряна/восстановлена → увести выходы в безопасное положение при обрыве.
   - `Арбитр` — несколько источников одного значения (крутилка, сервер, UI); **режим по умолчанию: последний пришедший побеждает**. Выход: значение + `source` (кто сейчас главный). Другие режимы (приоритет с таймаутом, ручной переключатель) — потом, по необходимости.
3. **Транспорты** (сервер в той же сети; один реестр команд на все транспорты):
   - **MQTT 5** — основной. Подключение к брокеру из настроек (адрес, логин/пароль, опц. TLS) **или** локальный брокер на самой плате (`mosquitto` 2.0.22 уже стоит, выключен; включать с паролем, конфиг — в персистентном каталоге `.pioneer`, т.к. `/etc` слетает при soft_reset; `install.sh` восстанавливает). Клиент — `paho-mqtt` (чисто питоновский, вендорится; на плате нет).
   - **HTTP** — `POST /pioneer/api/remote/cmd/<name>` с API-ключом → синхронный ответ (тот же контракт). Удобно для curl и простых серверов.
   - WebSocket-клиент к серверу — не нужен, пока сервер в той же сети (вернуться, если появится внешний сервер за NAT).
4. **Формат — простой JSON.**
   - Топики: `pioneer/<device_id>/cmd/<command>` (запрос), ответ — в `response_topic` из MQTT 5-свойств, иначе в `pioneer/<device_id>/resp/<command>`; корреляция — MQTT 5 `correlation_data`, иначе поле `id` в теле.
   - Запрос: `{"id": "abc", "args": {"angle": 90}, "ttl_ms": 5000}`; ответ: `{"id": "abc", "ok": true, "result": {...}}` / `{"id": "abc", "ok": false, "error": "..."}`.
   - Телеметрия: `pioneer/<device_id>/state/<name>` (retained), события: `pioneer/<device_id>/event/<name>`.
   - Статус: `pioneer/<device_id>/status` = `online`/`offline` (retained + LWT).
   - Discovery: `pioneer/<device_id>/describe` (retained) — список команд/состояний/событий со схемами, версия проекта.
   - `device_id` — стабильный ID из OTP (см. [002](002-vendor-docs-impact.md) п.8) + человекочитаемое имя в настройках.
5. **Home Assistant MQTT discovery — из коробки** (опция в настройках): команды → `button`/`number`/`switch`/`select`, состояния → `sensor`/`binary_sensor`. Полезно и коллегам с промышленными внедрениями. Позже — подумать о Sparkplug B для промышленного MQTT (не сейчас).
6. **Надёжность:**
   - TTL команды (`ttl_ms`, дефолт из настроек): протухшие после переподключения не выполняются, отвечают `expired`;
   - QoS 1 для команд/ответов, дедупликация по `id` (окно последних N id);
   - очередь исходящей телеметрии при обрыве — ограниченная, со сбросом старого.
7. **Безопасность:** только объявленные команды и валидация аргументов по схеме; логин/пароль брокера, опц. TLS; API-ключ для HTTP; лимит частоты на команду; журнал входящих команд в UI (кто, что, результат, время обработки); команды идут через тот же граф и захваты — безопасные состояния и запреты не обходятся.
8. **Несколько проектов:** имя команды уникально среди запущенных проектов; конфликт при старте проекта — как с захватом выходов («`servo.set` уже объявлена проектом X»).
9. **Скрипты/Python-блоки** получают то же через SDK: `@command("servo.set", angle=Number(0, 180))`, `self.publish(...)`, `self.state["angle"] = ...`.

## Железный нюанс: серва

- Нужен PWM 50 Гц, импульс 1–2 мс. Soft-PWM на плате с джиттером до 0.1 мс → до ~18° дрожания — **не годится для серв**.
- Рекомендуемо: **модуль PCA9685** (I2C, 16 каналов аппаратного PWM) — первый кандидат в модули (идея 001) вместе с нодой «Серва»; альтернатива — аппаратный PWM на J9-11/13 ценой выключения I2C3 m0.
- Питание сервы — отдельные 5 В, общая земля с Napi; сигнал 3.3 В большинство серв принимают.

## Пример сценария (критерий готовности)

Крутилка (потенциометр на ADC0 через делитель) → `Map Range 0..1.8 В → 0..180°` → `Арбитр` ← `Команда servo.set (angle)` → `Серва (PCA9685 ch0)`; `Арбитр.value` → `Состояние servo.angle`; `Команда` → `Ответ` с фактическим углом. Сервер: `mosquitto_pub -t pioneer/<id>/cmd/servo.set -m '{"id":"1","args":{"angle":90}}'` → серва на 90°, ответ `{"id":"1","ok":true,"result":{"angle":90}}`; повернул крутилку → управление вернулось к ней, `state/servo.angle` обновился.

## Открытые вопросы

1. Схема аргументов: свой мини-формат или JSON Schema-подмножество (для HA discovery и валидации).
2. Ответ на команду, если граф обрабатывает её несколькими ветками (два `Ответ` на один `Request` — ошибка валидации или «первый выиграл»).
3. Локальный брокер на плате: включать ли по умолчанию, и как жить вместе со штатным использованием mosquitto в NapiLinux (telegraf-конфиги производителя).
4. Нужен ли «режим только телеметрии» без приёма команд (read-only интеграции).
